# obsidian-knowledge-search — как правильно пользоваться MCP-сервером Smart Connections

Этот скилл описывает контракт и корректные паттерны работы с MCP-сервером `smart-connections` v2.2.2, который предоставляет агенту доступ к Obsidian-vault'у через заранее вычисленные плагином Smart Connections эмбеддинги.

Ключевая идея: **сервер возвращает структурированные ссылки на заметки и разделы + обогащённый контент**, а агент обязан интерпретировать их с учётом архитектуры индекса (три уровня блоков, RRF-шкала, cap'ы и т.п.). Без понимания этих особенностей легко дать пользователю поверхностный или неточный ответ даже при корректной работе самого сервера.

---

## 1. Когда применять скилл

Применяй этот скилл, когда в сессии доступны MCP-инструменты с префиксом `smart-connections-*` (точное имя зависит от конфигурации MCP-клиента — в `.mcp.json` пользователь может называть его, например, `smart-connections-develop`).

Явные триггеры в сообщениях пользователя:

- «Что у меня есть про <тема>?» / «Покажи материалы про <тема>».
- «Как в моих заметках сказано про <X>?» / «Объясни <X> на основе моих заметок».
- «Найди заметки, похожие на <Note>» / «Какие связанные темы у заметки <Note>?».
- «Построй карту связей / mind-map / граф от заметки <Note>».
- «Открой заметку <Note>» / «Прочитай раздел <Note#Section>».
- «Разреши ссылку `[[...]]`» / любая wikilink или obsidian:// URI в запросе.
- «Собери резюме / конспект по теме <X> из моих заметок».
- «Процитируй что у меня написано про <X>».

Не применяй скилл для общих вопросов к LLM без отсылки к vault'у пользователя. Если сомневаешься — сначала вызови `get_stats`, чтобы убедиться что сервер жив и vault подключен.

## 2. Архитектура и ключевые концепты

Понимание устройства индекса обязательно, иначе невозможно интерпретировать ответы.

### 2.1. Заметки (notes) и блоки (blocks)

Smart Connections индексирует vault на двух уровнях:

- **Нота (note)** — одна запись на файл. Один эмбеддинг на всю заметку.
- **Блок (block)** — подраздел заметки, привязанный к цепочке заголовков. Один эмбеддинг на блок.

По умолчанию все поисковые инструменты работают на уровне **блоков** (`granularity: "block"`) — это даёт точность попадания в раздел. Переключай на `"note"` только для обзорных задач («похожие заметки в целом»), например при построении карты связей.

### 2.2. Три уровня блоков (это критично)

Для одной и той же заметки Smart Connections индексирует **параллельно три уровня** блоков, и все три могут попасть в топ-N поисковой выдачи:

| Уровень | Пример ключа | Типичный размер | Содержит |
|---|---|---|---|
| `##`-раздел целиком | `Note.md##Section` | 100–150 строк (3 000–6 000 симв.) | заголовок + все вложенные `###` + код + таблицы |
| `###`-подраздел | `Note.md##Section#Sub` | 10–30 строк | один подраздел без детей |
| `#{N}`-фрагмент | `Note.md##Section#{1}` | 1–10 строк | преамбула между заголовком и первым подзаголовком, или технический чанк |

**Правило №1 (ключевое):** если `heading` оканчивается на `#{N}` — это фрагмент. Фрагменты почти всегда содержат topic-фразу без самого ответа. Сервер пытается помочь и автоматически подменяет контент на родительский раздел через поле `section_content`. **Всегда используй `section_content` когда он есть, не excerpt.**

### 2.3. Ссылки на блоки — compound key и (path, heading)

Блок адресуется двумя способами:

- **Compound key**: `"Folder/Note.md##Section#Subsection"` — всё одной строкой, разделитель между путём и цепочкой заголовков = первый `#`.
- **Пара (path, heading)**: `path="Folder/Note.md"`, `heading="##Section#Subsection"` (ведущие `#` обязательны).

Оба формата принимают `get_block_content` и `search_blocks`. Если нашёл блок в выдаче `search_notes`, copy-paste его `path` + `heading` в `get_block_content` — это работает.

### 2.4. Шкала similarity

Критично для правильной интерпретации:

- В **semantic mode** и во всех инструментах кроме `search_notes hybrid` — `similarity` — это **cosine similarity** в диапазоне [0, 1]. `0.85` означает «очень похоже», `0.4` — «слабо связано».
- В **`search_notes` при `mode: "hybrid"`** (режим по умолчанию!) — `similarity` — это **RRF-score**, обычно в диапазоне ~0.005–0.02. Это не cosine! `0.011` **не** означает «плохое совпадение», это **топовая позиция в ранжировании**.
- В **hybrid** ответе дополнительно присутствуют `rank_score` (нормализованный к [0, 1], top-1 = 1.0) и `raw_rrf_score` (копия RRF). Используй `rank_score` для сравнений «насколько топовый этот hit».

**Никогда не сравнивай `similarity` между hybrid и semantic/cosine-инструментами напрямую — они в разных шкалах.**

## 3. Карта инструментов: какой tool под какую задачу

Всего 9 инструментов. Выбирай по намерению пользователя, а не по ключевым словам.

| Намерение пользователя | Инструмент |
|---|---|
| Свободный запрос «что у меня есть про X» | `search_notes` (mode=hybrid по умолчанию) |
| «Что похоже на заметку Y» | `get_similar_notes` |
| «Что похоже на раздел Y#Z» | `search_blocks` |
| «Открой/прочитай заметку Y полностью» | `get_note_content` |
| «Прочитай раздел Y#Z полностью» | `get_block_content` |
| «Карта связей / сеть от Y» | `get_connection_graph` |
| «Разреши `[[...]]` или `obsidian://` URI» | `resolve_link` (потом `get_*_content`) |
| «У меня есть вектор X, найди ближайших соседей» | `get_embedding_neighbors` (низкоуровневое) |
| Диагностика: активная модель, vault, размеры | `get_stats` |

Правило выбора между `search_notes` и `get_similar_notes`: если есть **текстовый запрос** — `search_notes`; если есть **ссылка на заметку** пользователя — `get_similar_notes`.

## 4. Формат ответа сервера

Все поисковые инструменты возвращают JSON со структурой:

```jsonc
{
  "meta": {
    "vault_name": "Develop",
    "model_key": "bge-m3:latest",
    "dims": 1024,
    "semantic_available": true,
    "total_notes": 141,
    "total_blocks": 11796,
    "execution_ms": 37,
    "fusion": { "k": 60, "semantic_weight": 0.7, "keyword_weight": 0.3 },
    // только для search_notes:
    "search_mode": "hybrid",
    "fallback_from": null,
    "warnings": [],
    // когда expand применено:
    "expansion": {
      "mode": "high-similarity",
      "threshold": 0.8,
      "max_chars": 5000,
      "applied_count": 3,
      "skipped_count": 2
    },
    // когда dedup включено:
    "dedup": { "enabled": true, "level": 2, "groups_collapsed": 4 }
  },
  "results": [
    {
      "path": "01 MASTRA/Mastra 4- Память.md",
      "heading": "##Структурированная Working Memory#{1}",
      "lines": [1071, 1195],
      "similarity": 0.87,               // cosine (или RRF в hybrid)
      "excerpt": "...",                 // обрезано до excerpt_chars (дефолт 1500)
      "excerpt_truncated": true,
      "vault_name": "Develop",

      // появляются если сервер применил expand-to-section:
      "section_content": "...",         // ПОЛНЫЙ markdown родительского раздела
      "section_heading": "##Структурированная Working Memory",
      "section_lines": [1050, 1280],
      "expansion": {
        "applied": true,
        "reason": "fragment auto-expand",
        "original_heading": "##Структурированная Working Memory#{1}",
        "truncated_to_max_chars": false
      },

      // появляется если dedup свернул соседние hits:
      "sibling_matches": [
        { "heading": "##Структурированная WM#Пример Zod", "similarity": 0.83, "lines": [...] }
      ],

      // только в hybrid:
      "rank_score": 1.0,
      "raw_rrf_score": 0.0164
    }
  ]
}
```

**Как читать этот формат агенту:**

1. Посмотри `meta.expansion.applied_count` — сколько hit'ов получили section_content.
2. Для каждого hit проверь в таком порядке:
   - `section_content` — если есть, используй его как основной источник ответа.
   - Иначе `excerpt` — используй, но если `excerpt_truncated: true` и вопрос глубокий — зайди `get_block_content`.
3. `sibling_matches` — «в этом же разделе ещё N подблоков совпали». Не нужно отдельно их читать, раздел уже в `section_content`.

## 5. Правила работы с результатами (критично)

### 5.1. Фрагменты `#{N}` — всегда expand

Если в `heading` хита видишь окончание `#{1}`, `#{2}` и т.п. — это автоматически расширенный фрагмент. Сервер уже подтянул `section_content` родителя. **Не вызывай дополнительно `get_block_content` по фрагменту** — это даст те же 1–10 строк topic-фразы.

Если `section_content` по какой-то причине отсутствует (`expansion.applied: false, reason: "parent block not in index"`) — тогда вызови `get_block_content(path, heading=<heading без #{N}>)`, чтобы получить родительский раздел.

### 5.2. excerpt_truncated + важный hit → читай полностью

Если `excerpt_truncated: true` и **без этого hit'а ответ будет неполным** — вызови `get_block_content` чтобы получить полный текст раздела. `excerpt` по дефолту 1500 символов — это ~25–50% типичного `##`-раздела.

### 5.3. Дедупликация уже сделана сервером

По умолчанию `deduplicate_by_section: true`. Если несколько блоков из одного раздела попали в выдачу — сервер оставил лучший и переместил остальные в `sibling_matches`. **Не вызывай get_block_content отдельно по каждому sibling** — они все из одного `##`-раздела, используй уже полученный `section_content` (если есть) или один `get_block_content` по `##`-родителю.

### 5.4. Не путай шкалы similarity

Повторяю: в hybrid `similarity=0.011` — это **отличный** результат (top-1), а не плохой. Для сортировки по уверенности используй `rank_score` (0..1). Для перехода от hybrid-hit'а к оценке «насколько это реально близко» — вызови `get_similar_notes` по path найденной заметки; там `similarity` — cosine.

### 5.5. Большие заметки — full: true

Если `get_note_content` вернул `meta.truncated: true` — server-cap сработал. В v2.2.2 дефолт **1 000 000 символов** (~250-330k токенов русского), раньше было 200 000. Cap переопределяется env `MAX_NOTE_CONTENT_CHARS` на стороне сервера. Добавь `full: true` при повторном вызове если нужен полный текст — это безопасно, security-guard (path containment, whitelist) работает в обоих режимах. Но помни: клиентский MCP token-limit — отдельное ограничение, его сервер не обходит; если клиент режет ответ раньше server-cap'а, используй `get_block_content` для чтения по разделам.

Отдельно: на огромных заметках (100+ заголовков) JSON-ответ может всё равно упереться в токен-лимит клиента за счёт `blocks[]`. В v2.2.1 появились параметры `include_blocks_list: false` и `max_blocks` — выставляй их, если клиент режет ответ по длине. В `get_similar_notes`/`search_notes` (note-granularity) `blocks[]` теперь **по умолчанию не возвращается** — запрашивай явно через `include_blocks_list: true`, если он реально нужен (обычно достаточно `path` + `get_note_content`).

### 5.6. Дефолтные параметры не всегда оптимальны

- `limit=10` — нормально для обзорного запроса. Для глубокого вопроса с 1–2 явными ответами — ставь `limit=3` чтобы сфокусировать контекст.
- `threshold=0.5` — отфильтровывает явно нерелевантное в cosine-шкале. В hybrid игнорируется (применяется только к semantic-компоненте до fusion).
- `expand_threshold=0.8` — если нужно расширять более широко, снижай до 0.6–0.7. Не повышай выше 0.85: cosine редко достигает 0.9+.
- `expand_max_chars=5000` — поднимай до 10000 для очень развёрнутых вопросов; снижай до 2000 если контекст ограничен.
- `deduplicate_by_section=true` — оставляй. Единственный кейс снять: если явно нужно сравнить несколько подразделов одной `##`-секции (редкость).
- `include_blocks_list=false` (v2.2.1, поиск) / `true` (get_note_content) — по умолчанию оптимально. Выставляй в `true` на поиске только если нужна карта подразделов по нескольким заметкам сразу; в `false` на `get_note_content` — если заметка огромная и клиент режет ответ.

## 6. Research-паттерн для глубоких вопросов

Для запросов формата «объясни X из моих заметок», «какие есть способы Y», «собери конспект Z» используй следующий паттерн:

1. **Разведка:** `search_notes` с `mode: "hybrid"` (дефолт), `limit: 5`, `granularity: "block"`. Получи набор hits.
2. **Анализ meta:** проверь `meta.semantic_available` (если false — Ollama недоступна, результаты по keyword → предупреди пользователя), `meta.expansion.applied_count` (сколько hits расширены).
3. **Ранжирование:** определи 1–2 самые релевантные **заметки** (часто = hits с самым высоким rank_score или несколько hits из одной заметки).
4. **Углубление:**
   - Если hit с `section_content` покрывает ответ → используй его напрямую.
   - Если нужен контекст всей заметки → `get_note_content(path, full: true)`.
   - Если нужно несколько разделов → несколько `get_block_content` по разным `heading`.
5. **Связность:** для вопросов «как X связано с Y» — `get_connection_graph(root_note, depth=2)`.
6. **Синтез:** сформулируй ответ с прямыми цитатами (по возможности) и ссылками на конкретные файлы + разделы в формате `[Name](path#section)`. Используй `path` из ответов сервера, не выдумывай пути.

Для быстрых фактологических вопросов достаточно шагов 1–4.

## 7. Примеры типичных цепочек вызовов

### Пример 1 — глубокий вопрос, требующий чтения раздела

**Пользователь:** «Как в Mastra настроить память с Zod-схемой и удалить поле из неё?»

**Цепочка:**

```
1. search_notes({
     query: "память Mastra Working Memory Zod схема удалить поле",
     mode: "hybrid",
     limit: 5
   })
   → top-1 hit c heading "##Структурированная Working Memory#{1}",
     section_content уже есть (fragment auto-expand), section_lines=[1071, 1195].
2. Читаем section_content — видим инструкцию:
   «для удаления поля установи его в null».
3. Формируем ответ с цитатой + ссылкой [файл](path#Структурированная...).
```

Без expand-to-section понадобился бы шаг `get_block_content`, что стоило бы лишнего tool-call.

### Пример 2 — обзорный вопрос по теме

**Пользователь:** «Что у меня есть про observability агентов?»

**Цепочка:**

```
1. search_notes({ query: "observability и трейсинг агентов", mode: "hybrid", limit: 5 }).
   → dedup: 5 результатов из 3–4 разных заметок, у части sibling_matches.
2. Агент видит, что hit'ы сгруппированы: 2 раздела из Mastra 13, 1 из Mastra 1, 2 из deep-research.
3. Ответ: перечисление источников с кратким описанием каждого (по excerpt/section_content):
   - [Mastra 13 · Observability API](path#Часть 13.8) — ключевые концепции.
   - [Mastra 1 · Mastra Studio](path#Инспекция логов) — практика через Studio.
   - [Mastra Deep Research · мониторинг](path#раздел) — общий обзор подходов.
```

### Пример 3 — разрешение wikilink

**Пользователь:** «Что написано в `[[Mastra 4- Память#Structured Memory]]`?»

**Цепочка:**

```
1. resolve_link({ link: "[[Mastra 4- Память#Structured Memory]]" })
   → path="01 MASTRA/.../Mastra 4- Память (Memory).md", heading="#Structured Memory"
2. get_block_content({ path, heading })
   → полный markdown раздела.
3. Пересказ ключевых пунктов + ссылка на заметку.
```

Если `resolve_link` вернул `warnings: ["note not found"]` — проверь с пользователем правильность имени или используй `search_notes` как fallback.

### Пример 4 — карта связей

**Пользователь:** «Построй карту связей от заметки `Mastra — TypeScript-фреймворк`».

**Цепочка:**

```
1. get_connection_graph({ note_path: "...", depth: 2, threshold: 0.6, max_per_level: 5 })
2. В ответе дерево: root → children (до 5 на уровень) → внуки.
3. Визуализируй как bullet-list с указанием similarity каждого ребра.
```

## 8. Антипаттерны (чего НЕ делать)

- ❌ **Отвечать только по `excerpt`, если `excerpt_truncated: true` и вопрос требует точной цитаты.** Вызови `get_block_content`.
- ❌ **Повторять одно и то же содержимое из нескольких `sibling_matches`.** Сервер уже сказал тебе, что они из одного раздела — используй section_content один раз.
- ❌ **Использовать `get_note_content` без `full: true` для больших заметок.** Проверяй `meta.truncated` — если `true`, перезапрашивай с `full`.
- ❌ **Сравнивать `similarity` в hybrid (~0.011) с cosine (0.85) в одном рассуждении.** Используй `rank_score` для hybrid или переключайся на `mode: "semantic"`.
- ❌ **Искать связи через цепочку из 5+ `search_notes`.** Используй `get_connection_graph` — он оптимизирован и избегает циклов.
- ❌ **Пытаться найти блок вызовом `search_notes` по его heading.** Для ссылки `[[...]]` — `resolve_link`. Для похожего раздела — `search_blocks` или `get_similar_notes`.
- ❌ **Игнорировать `meta.warnings`.** Там живут fallback-from-semantic, fuzzy-matched уведомления, vault mismatch — все важные сигналы.
- ❌ **Выдумывать пути к заметкам в ответе.** Копируй `path` из `results` сервера один к одному.
- ❌ **Ставить `deduplicate_by_section: false` без причины.** Дефолт улучшает охват; снимай только если явно нужны подразделы одной секции.

## 9. Типичные ошибки и их разрешение

| Сообщение сервера | Причина | Что делать |
|---|---|---|
| `Block not found: <key>` | Ключ не существует в индексе. Заметка удалена/переименована; heading изменён | Проверить `get_stats`, `search_notes` по тексту раздела. Возможно Smart Connections ещё не переиндексировал — попросить пользователя запустить переиндексацию в Obsidian. |
| `Block line range unknown for <key>` | Блок есть, но у него нет `lines` (это бывает для некоторых legacy-блоков) | Вернуть пользователю, что конкретный блок не имеет диапазона; использовать `get_note_content` на соответствующей заметке. |
| `embedding_vector has N dims, expected M (model: ...)` | Ты передал неверный размерности вектор в `get_embedding_neighbors` | Получить `dims` через `get_stats` и подогнать вектор. |
| `Note not found: <path>` | Путь неверный (опечатка, регистр, лишние слеши) | Проверить, как path выглядит в предыдущих ответах сервера — вайка-релативные пути с учётом регистра обязательны. |
| `semantic requested but Ollama is not configured — falling back to keyword` | На сервере Ollama отсутствует или не проходит health-check | Предупредить пользователя: семантический поиск недоступен. Можно попросить проверить что Ollama запущен (`http://localhost:11434`). |
| `Ollama embed failed: <...> — falling back to keyword` | Сеть/модель/тайм-аут на стороне Ollama | Попробовать ещё раз; если повторяется — сообщить пользователю про проблему с Ollama. |
| `fuzzy-matched: requested "X" resolved to "Y"` | `warnings` на `get_block_content` или `search_blocks` — найден через нормализацию | Не ошибка, информация. Использовать `Y` как canonical heading в последующих вызовах. |
| `contains ../ segment` / `File extension "..." is not permitted` | Попытка вырваться за пределы vault или прочитать не-markdown | Проверить путь — по дизайну можно читать только `.md/.markdown/.canvas` внутри vault. Не эскалировать. |

## 10. Быстрая памятка (quick reference)

Перед первым вызовом в сессии:

```
1. get_stats() — узнать vault_name, model_key, dims, semantic_available, totals.
```

При свободном запросе:

```
2. search_notes({ query, mode: 'hybrid', limit: 5 }) — по умолчанию.
3. Для каждого hit проверить section_content / excerpt_truncated / sibling_matches.
4. При необходимости — get_block_content или get_note_content(full:true).
```

При ссылке на заметку/раздел:

```
2. resolve_link(link) → get_note_content(path) или get_block_content(path, heading).
```

При запросе карты связей:

```
2. get_connection_graph({ note_path, depth: 2, threshold: 0.6, max_per_level: 5 }).
```

Синтез ответа:

- Цитируй из `section_content` или `excerpt`.
- Ссылки: `[name](vault-relative/path#heading)`.
- Если ничего не нашлось — честно скажи, что в vault'е это не упоминается.
